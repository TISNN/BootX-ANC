# ANC 知识飞轮机制与落地实践

> 2026年8月 · 从机制原理到工程落地，附 WorkBuddy 场景实操方案

---

## 一、核心命题

ANC（AI Native Company）框架中，每个员工在本地用 Agent 工作。但**个人知识如何回流到企业知识库，形成持续进化的飞轮**？这是 ANC 落地的核心工程挑战。

**一句话结论**：没有回流的 AI 是高级一次性筷子，有回流的 AI 才是公司资产。

> 参考：ANC 框架全景解读见 [[anc-fde-research]]

## 二、知识飞轮的三层回流机制

知识飞轮不是"员工把文件传到共享盘"这么简单，是一条自动化流水线，分三层运转：

### 第一层：全量日志采集

所有 AI 交互——Prompt、模型返回、工具调用、生成文件——全部通过统一的 Gateway 中间件拦截并写入数据库。

```
员工 → AI 入口（唯一入口）
         ↓
    Gateway (:8000) ← 路由层
         ↓
    Logger 中间件 ← 拦截所有请求/响应
         ↓
    Postgres ← 全量存储（用户ID、助手类型、完整Prompt、完整返回、工具调用、token消耗、耗时）
```

关键设计：**日志写入是异步的，不阻塞员工工作流**。员工感知不到日志的存在。

> 参考：腾讯云开发者社区《实操记录--WorkBuddy 企业微信接入》，https://cloud.tencent.com.cn/developer/article/2644091

### 第二层：周期性知识清洗

飞轮的核心引擎。每周定时跑一次清洗任务，从原始对话中提炼可复用知识：

```
每周定时任务：
  读取上周所有 AI 交互记录
  → 按助手类型分桶（调研归调研桶，文档归文档桶）
  → 调用 AI 跑清洗 prompt：
      「从这批对话里提炼出：
       1. 高频问题 + 满意的回答模板
       2. 被否定的回答（用户追问/反驳的）
       3. 工具调用失败的场景 + 失败原因
       4. 涉及的具体公司内部数据（项目名、客户名、SOP编号）」
  → 输出结构化知识条目
  → 写入知识库目录
  → 自动同步到 RAG 向量库
```

**实测数据**（NGS AI Center）：第一周 RAG 命中率约 5%，第四周 30%，第八周 60%。员工能感知到的变化是：以前问 AI 一个项目，AI 说"请提供更多上下文"；八周后问同样的问题，AI 直接给出项目名、DRI、SOP 约束。

> 参考：《经验分享：用千问和开源AI工具，帮公司建成 AI Native 企业》，https://news.qq.com/rain/a/20260520A096DQ00

### 第三层：知识固化为 Agent 技能

飞轮最高形态——不是"让 AI 知道"，而是"让 AI 能干"。被验证有效的知识条目，进一步固化为 Agent 技能（Skill），分发到全员。

ANC 项目（GitHub: zzhiyuann/anc）的做法：每个 Agent 在完成任务后自动写回顾（retrospective），这些回顾被注入到后续任务中，Agent 的行为模式随着使用不断进化。

> 参考：ANC 开源项目，https://github.com/zzhiyuann/anc/

## 三、Lite 模式 vs Host 模式的知识回流差异

| 环节 | Lite 模式 | Host 模式 |
|------|----------|----------|
| **知识存储位置** | 员工本地 + GitHub 共享仓库 | 中心服务器 |
| **同步方式** | Git push/pull + 定时清洗任务 | 实时写入中心数据库 |
| **知识清洗** | 仍需中心化的清洗管线（GitHub Actions 或定时任务） | 服务端直接跑清洗任务 |
| **RAG 检索** | 本地向量库（需定期拉取中心知识库更新） | 统一中心向量库，实时命中 |
| **Agent 技能分发** | 通过 Git 仓库分发 Skill 配置文件 | 服务端推送 |

Lite 模式的核心挑战在于**同步时效性**。但清洗任务仍然是中心化的——日志从各员工本地汇聚到中心数据库，清洗在中心端完成，知识条目再分发回各员工的本地向量库。

## 四、Akasha 三层记忆架构：理论框架

开源项目 Akasha AI 提供了更系统的理论模型，把知识回流拆成三个记忆层：

| 记忆层 | 存什么 | 怎么回流 | 例子 |
|--------|--------|---------|------|
| **事实记忆** | 发生了什么——文档、会议、代码、工单、对话 | 自动采集+权限标注+新鲜度评分 | 某次客户会议纪要、某段代码提交记录 |
| **交互记忆** | 为什么重要——决策、分歧、权衡、假设 | 从对话中提取决策链+推理过程 | "为什么选了方案A而不是B"的讨论记录 |
| **行动记忆** | 下一步做什么——SOP、工作流、技能、护栏 | 从成功/失败中学习，更新 SOP | 某个客服场景的标准回复模板 |

Akasha 的核心洞察：**"知识库等待被搜索；记忆主动参与行动。"** 传统知识库是静态的，ANC 的记忆是活的——它不只是"存着"，而是主动在需要时出现，并随着使用不断进化。

> 参考：Akasha AI 项目，https://github.com/chaterm/Akasha

## 六、落地路径：三种方案

### 方案一：不采集日志，采集"产出"（推荐起步）

WorkBuddy 的对话日志不好拿，但员工用 WorkBuddy 产出的东西是明确的——文档、代码、方案、分析报告。追着产出跑，不追着对话日志跑。

**操作方式**：
1. 定规则：所有人用 WorkBuddy 做完工作后，最终产出物必须落到共享知识库（飞书文档、Notion、Obsidian Git 仓库等）
2. 每周一次，把本周新增的产出物批量喂给 AI 做清洗，提炼知识点
3. 知识点同步到 RAG 向量库

**优点**：零开发成本，立即能跑。**缺点**：舍弃了对话过程中的隐性知识（如"试了三种方案才找到对的"）。

### 方案二：WorkBuddy 对话导出 + 定期清洗

WorkBuddy 支持对话导出功能。每个员工每周五执行一次导出，放到共享目录，清洗任务跑在共享目录上。

**注意**：这是"人肉流水线"，靠员工自觉，漏一两次流程就断了。适合 3-5 人小团队试水阶段。

### 方案三：搭建统一 Agent 入口（长期方案）

团队规模 8 人以上时值得投入。部署 Open WebUI 或类似界面，背后接各种模型 API，中间加一层 Logger 自动拦截所有请求写入数据库。每周清洗任务自动跑。

NGS 用 6 天搭完了整套 Gateway。投入 1-2 周，之后完全自动化。

> 参考：腾讯 WorkBuddy Enterprise API 文档，https://cloud.tencent.com/document/product/1831/134441

---

## 七、实施建议

**先用方案一跑起来。** 飞轮的核心不是技术完美，而是"先用起来，再优化"。哪怕只采集到 30% 也比完全不采集强。用一个月，能看到哪些知识在重复、哪些坑在反复踩，那时候再决定上方案三。

**门槛不在技术**——Gateway + Postgres + 每周清洗任务，NGS 用 6 天就搭完了——**门槛在于有没有把"知识回流"当成基础设施来建，而不是当成"以后再说"的附加功能。**
