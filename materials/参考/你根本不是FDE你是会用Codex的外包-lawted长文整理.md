# 你根本不是 FDE，你是会用 Codex 的外包

来源：抖音 lawted 长文字文章  
主题：FDE、AI Native、ANC、传统企业 AI 落地  
状态：基于粘贴长文整理，已保留原文。原文中多处提到 OpenAI、Palantir、OECD、NBER 等链接，但粘贴文本未包含具体 URL，后续引用前需要补证据链接。

## 一句话

真正的 FDE 不是用 Codex 更快地给客户搓一套 SaaS，也不是给老板做一个会说话的 AI Dashboard，而是进入企业现场，从真实任务出发，帮助企业长出一根能吸收 Context、组织人和 Agent、把反馈变成行动的 AI Native 树干。

## 核心判断

这篇文章反对一种伪 FDE 路线：先梳理 SOP，再上软件，再积累数据，最后接 AI。

作者认为，这条路线本质上还是过去二十年的传统数字化，只是把 BI 大屏改名成 AI Dashboard，把传统外包改成 Vibe SaaS。它能让老板更快看到问题，却不能让系统参与解决问题。真实动作仍然发生在微信、Excel、人工催办和线下协调里。

作者真正强调的是倒过来的路线：AI 应该从第一天进入真实业务，从聊天、文件、表格、PDF、邮件和现场反馈中理解企业，一边解决具体问题，一边沉淀数据、流程、权限、Skill 和反馈机制。

## 作者反对什么

### 1. 把 FDE 做成传统软件实施

传统路线是：

```text
SOP -> 软件 -> 数据 -> AI
```

作者认为这不是 FDE，而是传统软件实施公司的老路：先流程咨询，后 ERP，再培训员工填表，等数据库积累起来，再接一个大模型接口。

问题是，这条路并没有改变企业的真实运转方式。它只是让数据更容易被看见，而不是让组织更容易行动。

### 2. 把 AI Dashboard 当成企业 AI 落地

AI Dashboard 的典型场景是：老板问“这个月哪个项目亏得最多”，屏幕上跳出一张漂亮图表。

但下一步仍然是人去找人、人去催人、人去翻聊天记录、人去决定怎么处理。系统只负责展示，行动仍然在系统之外发生。

作者认为，这种交付只是“更聪明的屏幕”，不是企业 AI Native 改造。

### 3. 把 Vibe Coding 变成 Vibe SaaS

FDE 进客户现场坐两天，用 Codex 或 Claude Code 很快搓出一个系统，页面漂亮，数据能展示，演示时老板觉得很厉害。

但三个月后，员工继续在微信里沟通，Excel 继续在群里飞，系统里只剩演示当天录进去的数据。

作者认为，这只是把昂贵的定制 SaaS 变成更便宜、更快的定制 SaaS。开发成本下降了，但方向没有变化。

## 作者主张什么

### 1. 从关键决策和关键动作倒推系统

作者引用 Palantir Foundry 和 Ontology 的思路：不是先问客户有多少表、多少数据库、多少接口，而是先问企业每天有哪些重要决策，谁在什么情况下做，做完之后会改变什么。

真正的系统不只需要名词，还需要动词：

- 客户、订单、库存是什么
- 谁能改订单
- 什么时候触发采购
- 异常发生后找谁
- 哪些动作需要审批
- 哪些动作可以自动执行

也就是说，AI Native 改造应该从 Action 往 Data 倒推。

### 2. AI 不只是消费结构化数据，也能生产结构化数据

传统数字化认为，企业要先有结构化数据，AI 才能用。

作者认为现在顺序可以反过来。模型已经能理解过去不被软件承认的数据：

- 一张纸
- 一段语音
- 一段微信群里的老板指令
- 一份 PDF
- 一张 Excel
- 一封邮件
- 一段老师傅的经验描述

比如老板在群里说：“这批货先发，月底再收钱。”这里面已经包含客户、订单、账期、优先级和授权。以前软件听不懂，所以员工必须重新填表。现在 AI 可以先读懂，再生成待确认状态，并把风险点交给人签字。

关键变化是：

```text
不是员工先学会使用系统，
而是系统先学会理解员工。
```

### 3. SOP 可以是 AI 参与业务后的结果

作者不认同“SOP 是 AI 进场前的作业”。

很多中小企业口头上有 SOP，但老板说一套，员工说一套，真实执行又是第三套。咨询公司访谈一个月，可能得到一张每个人都认可、但没有人真正执行的流程图。

AI Native 的机会，是让系统从真实发生的任务中认识企业，而不是先要求企业把自己描述成一套标准答案。

所以新的路线更像：

```text
真实任务 -> AI 介入 -> Context 积累 -> 流程沉淀 -> Skill 复用 -> 组织行动增强
```

## 树干与树叶

作者用“树干和树叶”解释 FDE 交付物。

树叶是一个个具体项目：

- PDF 转 Excel
- 进销存页面
- 报价生成器
- AI Dashboard
- 库存管理
- 项目管理后台

树叶当然有用，因为具体问题被解决，员工才愿意继续用，老板才知道钱花在哪里。

但如果 FDE 每次只交付一片叶子，每个问题都重新开发一套系统，企业会越来越碎，FDE 的维护债也会越来越重。

真正应该留下的是树干：

- 这家公司有哪些项目
- 项目现在处于什么状态
- 哪些人有什么能力
- 谁有权做什么决定
- 哪些聊天、文件、表格、现场反馈属于哪个业务 Context
- 哪些任务系统可以自己完成
- 哪些任务必须找人确认
- 人确认后的结果如何继续沉淀

树干一旦存在，今天做 PDF 解析长出一个 Skill，明天做报价可以继续复用客户、产品、历史价格，后天出现异常时系统可以找到负责人、准备方案、把需要拍板的部分送到对应的人面前。

## AI Dashboard 与 ANC 的区别

作者认为 AI Dashboard 和 ANC 的根本区别是：

| 维度 | AI Dashboard | ANC |
|---|---|---|
| 核心功能 | 给人看数据 | 和人一起干活 |
| 数据作用 | 集中展示 | 进入行动链路 |
| 问题处理 | 发现异常后等人处理 | 主动定位责任人、准备方案、推动下一步 |
| 交付结果 | 一块更聪明的屏幕 | 一套能持续吸收 Context 并组织行动的能力 |

作者对 ANC 的定义，可以理解为：企业 AI Native 状态下的组织操作系统。它不是某个页面，而是一根能持续沉淀 Context、权限、Skill 和反馈机制的树干。

## 没有 ERP 未必是劣势

作者提出一个反直觉判断：很多没有 ERP 的传统企业，可能反而更适合 AI Native 改造。

原因是它们没有太多遗留系统、历史接口、被旧软件写死的流程，也没有员工被某套系统训练出的固定操作习惯。

这是一张很脏的白纸，但仍然是一张白纸。

有 ERP 的企业当然也能做 AI，但它们可能面对另一种麻烦：几千张数据表、复杂权限、历史流程、责任边界、系统债务。看起来数据很多，真正能动的数据很少。

所以作者不认同“数字化基础越好，AI 改造天然越容易”。有数据是优势，但一堆互相冲突的系统不一定是优势。

## 真正的门槛不是有没有 ERP

作者最后把问题落到组织授权。

没有 ERP 不是最难的。真正难的是：

- 一号位是否愿意改变
- 企业是否愿意面对透明
- 是否有人愿意为改变负责
- 真实业务是否愿意交出来
- 信息不透明带来的利益是否愿意被触碰

一个采购流程为什么绕，可能不是大家没想清楚，而是有人需要它绕。一个库存为什么永远对不上，可能不是表格设计不好，而是“对不上”本身保护了某些利益。

技术把流程照亮的那一刻，也会照到一部分人不希望被看到的地方。

所以 FDE 的关键不是客户有没有数据库，而是企业是否给了改变组织的授权。

## 对 FDE 的定义

作者对 FDE 的定位是：

```text
FDE 不是一个拿着 Codex 的软件外包。
FDE 是企业进入 AI Native 状态时，最早的组织设计者。
```

FDE 要做两件事：

1. 找到足够具体、能产生显性收益的切口，让系统真的开始工作。
2. 从这次工作中留下可复用的 Context、权限、Skill 和反馈机制，让下一片叶子从同一根树干上长出来。

也就是说，FDE 不是从做一个小软件结束，而是从一个具体问题开始，验证价值，再抽象出能够规模化的模式。

## 可作为我们后续文章的论点

1. “会用 Codex 快速做系统”不是 FDE 的充分条件，甚至可能只是更快的软件外包。
2. 企业 AI 落地不能只停留在“看见问题”，必须进入“推动下一步行动”。
3. 没有 ERP 的传统企业不一定是低起点，它可能是 AI Native 改造的绿地。
4. SOP 不一定是 AI 进场前的前置条件，也可以是 AI 参与真实任务后沉淀出来的结果。
5. FDE 的真正资产不是页面，而是企业自己的 Context、权限、Skill 和反馈机制。
6. 客户真正买的不是软件，而是一种新的组织行动能力。
7. 如果一个 AI 项目最后只是让员工多填表、老板多看图，那它仍然是上一代软件。

## 可改写成短视频口播的钩子

你根本不是 FDE，你只是会用 Codex 的外包。

为什么这么说？

因为你进企业以后，干的还是过去软件公司那套东西：先梳理 SOP，再做系统，再接数据，最后给老板做一块会说话的大屏。

但企业缺的不是一块更聪明的大屏。

老板发现项目亏了以后，还是要找人、催人、翻聊天记录、开会、拍板。AI 只是让问题更快出现在屏幕上，没有真正参与问题的解决。

真正的 FDE 应该做的是另一件事：让 AI 从第一天进入真实任务，一边干活，一边理解企业，一边沉淀流程、权限、Skill 和反馈机制。

不是员工先学会使用系统，而是系统先学会理解员工。

```text
前台不一定要做新系统，
后台不能只做一次性脚本。

接上一套可复用、可审计、可持续生长的企业行动能力。
```

这不就是把过去昂贵的定制 SaaS，变成了便宜一点、快一点的定制 SaaS 吗。
开发成本下降了，方向没有变化。
我们当然可以用 AI 一天写完一个进销存系统。但真正需要问的，不是这个系统能不能一天写完，而是这家公司为什么二十年都没有成功用上进销存。
是以前的软件太贵，还是员工不愿意多填一张表？
是流程真的不清楚，还是流程一旦透明，有些人的利益就会受损？
是老板不知道库存，还是老板其实根本不靠库存数据做决策？
这些问题没搞懂，Codex 写得越快，死得也越快。
但搞懂以后，答案也不一定是上一套 ERP。
因为今天的模型，已经开始能够直接理解以前那些不被软件承认的数据了。
一张纸是数据。
一段语音是数据。
老板在群里说「这批货先发，月底再收钱」，里面已经有客户、订单、账期、优先级和一次真实的授权。
以前的软件听不懂这句话，所以员工必须再打开一个表单，把客户名称选一遍，把订单编号填一遍，把账期改一遍，再提交审批。
如果他不填，系统就认为这件事没有发生。
现在不一样了。
模型可以先读懂这句话，识别它对应哪个项目，找到之前的合同和聊天记录，生成一条待确认的业务状态，再把真正有风险的地方交给人签字。
员工不是先学会使用系统，系统先学会理解员工。
这一下，整个顺序就倒过来了。
这块不是一种对未来的想象，OpenAI 已经把它写进 Agent 的官方工程指南里了。
它说 Agent 最适合处理的，正是复杂决策、非结构化数据和那些特别脆弱的规则系统。因为 Agent 不只是回答问题，它可以跨工具执行一个端到端的工作流。OpenAI 的 Agent 指南在这里。
非结构化数据，以前是传统企业数字化最头疼的部分。
对 Agent 来说，反而是主场。
OpenAI 还有一个日本大日本印刷公司的案例，我看完觉得特别适合放在这里。那家公司把纸质手册、历史质量记录和老师傅脑子里的经验直接交给 ChatGPT Enterprise，让它一边读取，一边结构化，再进入内部知识系统。
结果不是先花几年建设数据中台。
他们定义数据架构的时间，直接下降了 90%。英文专利和设备原理的信息整理，原来要几个月，后来缩短到 3 天。完整案例在这里。
这个案例当然不能证明所有没有 ERP 的公司都会成功。但它至少已经把「必须先完成结构化数据建设，才有资格使用 AI」这条铁律打破了。
AI 不只消费结构化数据。
它也可以参与生产结构化数据。
那篇文章说，要先有 SOP，再有软件，再有数据，才轮得到 AI。
我现在越来越相信，很多传统企业真正可行的路线，应该是从真实任务直接开始。
AI 先进入员工原本就在使用的飞书、微信、Excel、PDF 和邮件里，持续收集 Context。每发生一次真实业务，它就多理解一点这家公司的人、项目、规则和例外。哪些任务可以自己完成，哪些任务必须找财务，哪些金额需要老板签字，哪种客户必须让销售亲自确认，都是在一次次执行里长出来的。
SOP 不是 AI 进场前必须交的作业。
SOP 可以是 AI 参与业务以后产生的结果。
这个区别特别重要。
传统软件假设企业已经知道自己怎么运转，软件只负责把这套流程固化下来。但现实里的大量中小企业根本不是这样。老板说有 SOP，员工说有另一套 SOP，真正干活的时候又是第三套。你让咨询公司采访一个月，得到的往往也是一套每个人都认可，但没有人真正执行的流程图。
画得巨漂亮。
挂墙上也巨合适。
就是跟公司每天发生的事没什么关系。
AI Native 的机会，恰恰是让系统从真实发生的任务里认识企业，而不是先要求企业把自己描述成一套标准答案。
这也是我们一直在讲的树干和树叶。
进销存页面是一片树叶，PDF 转 Excel 是一片树叶，报价生成器是一片树叶，AI Dashboard 也是一片树叶。
叶子当然有用。我们自己进入企业以后，也会从这些特别具体的东西开始做。因为只有一个具体问题被解决，员工才愿意继续用，老板才看得见钱花在了哪里。
但如果 FDE 交付完一片叶子就走了，下一次客户要做库存，又重新开发一遍。再下一次要做项目管理，再来一个新的后台。每解决一个问题，企业就多一套系统，FDE 就多一份维护工作。
做得越多，债越多。
真正应该留下来的，是树干。
它知道这家公司有哪些项目，项目现在是什么状态。它知道哪些人具备什么能力，谁有权做什么决定。它能接住聊天、文件、表格和现场反馈，把它们放回正确的业务 Context。它可以自己完成一部分任务，也可以在需要的时候调用一个人，并且把结果继续沉淀下来。
今天做 PDF 解析，企业多长出一个 Skill。
明天做报价，这个 Skill 可以继续读取昨天积累的客户、产品和历史价格。
后天出现异常，它不是在大屏上画一个红点等老板看见，而是找到负责人，给出原因，准备好可执行方案，把真正需要拍板的部分送到对应的人面前。
系统不只是知道发生了什么。
它开始推动下一步发生。
我觉得这才是 AI Dashboard 和 ANC 最根本的区别。一个是给人看的，一个是和人一起干活的。一个把数据集中起来，一个把组织真正运转起来。
回到没有 ERP 这件事。
有 ERP 的企业当然也能做 AI，但它们往往要先面对另一种麻烦。数据表有几千张，权限跟着部门走，流程被软件写死，任何一个 Agent 想做点事，都要穿过无数接口、审批和历史责任边界。
看起来数据很多，真正能动的数据很少。
连 OECD 在研究企业采用 AI 的成本时，都把适配遗留系统的集成成本单独列成了一项重要障碍。企业以前买过的系统越多，不一定越接近 AI。很多时候，只是要迁移的债更多。OECD 的原始分析在这里。
这也是为什么我不太认同「数字化基础越好，AI 改造就天然越容易」这句话。
有数据当然是优势，有一堆互相冲突的系统可不一定是。
有些大企业做了二十年数字化，到头来只是把纸上的部门墙，重新在数据库里砌了一遍。
而一家没有 ERP 的公司，如果老板真的愿意改变，反而可以不走这条弯路。它不需要先复制一遍上一代企业，再从上一代企业升级成 AI 企业。它可以直接围绕 Agent、Context、Skill 和人的协作方式，重新设计自己的工作。
这让我想到很多国家当年没有铺满固定电话，后来反而直接进入了移动通信。也有很多小商户没有经历完整的信用卡收单体系，直接用二维码开始做移动支付。
少上的那一课，不一定永远要补。
有时候，它给了你一次跨过去的机会。
经济学里还有一条很经典的证据，可以帮我们把这件事看得更清楚。
MIT 的 Erik Brynjolfsson 和几位学者长期研究信息技术为什么没有立刻带来生产率增长。他们把这个现象叫生产率 J 曲线。新技术刚进入企业时，效果经常很差，甚至先让效率下降。不是技术没有用，而是企业还没有完成与它配套的组织改变、流程重构和人员能力建设。
他们研究 AI 后给出的判断也一样，通用技术的价值，要等一整套互补创新出现以后才会真正释放。NBER 收录的生产率 J 曲线原始研究在这里。
你想想看，如果决定收益的关键是新的组织方式，那一家被旧系统和旧流程牢牢锁住的公司，未必比一张白纸更占优势。
以前投入的数字化资产是财富，也可能是路径依赖。
没有 ERP 的公司少了一座地基，但也少了一栋必须先拆掉的旧楼。
当然，这里有一个特别大的前提。
没有 ERP 的企业，在技术上可能是一片绿地，在组织上也可能是一片雷区。
文章里的公司，真正让 FDE 进不去的，并不是没有数据库，也不是员工不会使用软件。作者自己后来其实已经说出来了，领导不愿意改变，下面还有人依赖信息不透明获得利益。
这种情况下，你做 ERP 也好，做 ANC 也好，都会失败。
因为企业没有给你改变组织的授权。
一个采购流程为什么绕，可能不是大家没想清楚，而是有人就需要它绕。一个库存为什么永远对不上，可能不是表格设计得不好，而是对不上本身就在保护某些东西。技术把流程照亮的那一刻，也会照到一部分人不希望被看到的地方。
所以真正的门槛，从来不是企业有没有 ERP。
是企业的一号位，愿不愿意把门打开。
这也是为什么我不完全认同「传统企业没有需求，所以 FDE 只能去苦哈哈地通马桶」这个判断。
FDE 当然要干脏活。我们自己做过 PDF 转 Excel，也看过工厂里最不起眼的单据。业务里没有哪一种具体问题，因为听起来不够性感就不值得做。
但干脏活和永远做外包，是两回事。
通一次马桶，如果只留下一个定制脚本，那你下个月还要回来再通一次。
通完以后，把管道、压力、堵塞原因、负责的人和处理方式都变成企业可以持续使用的能力，下次系统能自己发现、自己处理，处理不了再叫人，这才是 FDE 应该做的事。
FDE 不是一个拿着 Codex 的软件外包。
他是企业进入 AI Native 状态时，最早的组织设计者。
他要找到一个足够具体、能够产生显性收益的切口，让系统真的开始工作。也要从这次工作里，留下可以复用的 Context、权限、Skill 和反馈机制。然后再让下一片叶子从同一根树干上长出来。
OpenAI 对自己的 FDE 团队有一句描述，我挺喜欢。他们不是从通用产品开始，而是先解决一个具体问题，验证它确实产生价值，再寻找能够规模化的模式。官方页面写得很清楚。
注意，它说的是从具体问题开始。
不是从做一个小软件结束。
这中间差的，就是一整家公司未来会不会越用 AI，越了解自己，越能自己进化。
所以看完那篇文章以后，我为什么会说「你根本没资格谈论 FDE」。
不是因为作者没有写过代码，也不是因为她没有在 Palantir 工作过。FDE 从来不靠一张工牌获得讨论资格。
是因为她明明看见了 FDE 要进入现场，却没有看见 FDE 进入现场以后，真正应该改变的到底是什么。
她依然站在传统软件的世界里，想象 AI 应该怎么进入企业。
在那个世界里，数据必须先进入数据库，流程必须先被写成 SOP，员工必须先学会使用软件，AI 才能在所有准备工作完成以后登场。
而我们正在看到的另一个世界，刚好反过来。
AI 可以从第一天就进入真实业务。它从混乱的聊天、文件和任务里开始工作，一边解决问题，一边帮助企业形成数据，一边把事实上的流程沉淀下来。软件不再是所有工作的入口，而是需要某种界面时，随时长出来的一片叶子。
如果交付到头来仍然是一套让员工多填表、让老板多看图、让数据继续停在屏幕里的系统，那你不是在做 FDE。
你只是借了 FDE 这个最新的名字，继续卖上一代软件。
企业缺的不是一块更聪明的大屏。
也不是一套用 Vibe Coding 三天搓出来的 ERP。
它缺的是一根能够不断吸收 Context、组织人和 Agent、把反馈变成下一次行动的树干。
这根树干，我们叫它 ANC。
这也是我们现在认为，FDE 真正应该推进的东西。
不是多做几个叶子，不是把 Vibe Coding 变成 Vibe SaaS，而是成为一家企业进入 AI Native 状态时的战略咨询和建设者。
所以，OpenAI 花 200 万年薪抢的人，在那家公司连门都进不去，这句话可能是对的。
但原因不是那家公司没有 ERP。
恰恰相反，没有 ERP，可能是它最值得进入的地方。
真正锁住那扇门的，是组织没有准备好面对透明，没有人愿意为改变负责，也没有一号位愿意把真实业务交出来。
门一旦打开，FDE 要做的也不是先搬一套旧时代的软件进去。
他应该带进去一颗种子。
让这家公司第一次，可以从自己的真实工作里，长出下一种组织。

中国大量没有 ERP 的传统企业，不是 AI 时代最差的一批学生。
它们甚至可能，是最有机会跳级的那一批。
至于那些还在研究怎么接完数据源，再给老板做一块 AI Dashboard 的人。
你们慢慢玩。
