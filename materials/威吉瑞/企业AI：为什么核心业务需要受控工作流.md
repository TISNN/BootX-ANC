# 企业 AI：为什么核心业务需要 Agent + 受控工作流

> 面向非技术读者的说明文档｜2026 年 9 月

## 先说结论

企业不是不该用 Agent，也不是要把 AI 关在聊天框里。

关键在于：**让 AI 理解人的意图，让系统负责承诺执行。**

当一件事需要反复做、涉及客户、资金、数据、权限或合规时，不能只靠 Agent 每次“临场判断”。企业应把关键步骤写进受控的业务工作流：谁可以做、做什么、如何校验、何时审批、出了问题谁负责，都要清楚。

一句话概括：

> 自然语言适合说清“想做什么”，程序化工作流适合保证“会怎样做、谁来负责”。

---

## 1. Agent 很能干，为什么还不够？

可以把 Agent 想成一位反应很快、会查资料、会使用工具的智能助手。

它特别适合：读合同、理解客户问题、整理会议纪要、搜索资料、生成草稿、处理少见的例外情况。遇到步骤不确定的问题，它能帮人探索路径。

但企业日常运行的很多工作，并不是“找到一个好答案”就结束了。例如：

- 一张发票能不能报销；
- 一笔付款能不能提交；
- 一个供应商能不能建档；
- 一份客户文件能不能对外发送；
- 一条生产订单能不能进入下一道工序。

这些事情不仅要做对，还要能回答：**依据是什么？谁批准的？系统改了什么？出了问题能不能追回？**

因此，Agent 可以参与，但不能独自承担最后的执行责任。

---

## 2. 个人 Agent 和企业业务系统，解决的不是同一类问题

像 Hermes、OpenClaw 这类通用 Agent 很适合个人或小团队：它们可以连接电脑、文件、聊天工具和各种服务，帮助完成多样化任务。

这并不代表它们“不适合企业”。真正的问题是：企业若要将它们接入核心业务，必须额外建设一层企业控制能力。

| 个人助手更关心 | 企业核心业务更关心 |
|---|---|
| 能不能把事办成 | 是否按授权、按规则、可追责地办成 |
| 我能否方便地使用工具 | 不同岗位是否只能使用被授予的工具和数据 |
| 这次回答是否有帮助 | 每一步是否留有证据、可回放、可审计 |
| 任务失败后我自己处理 | 失败后是否能重试、转人工、回滚或升级 |

OpenClaw 官方文档也把一个 Gateway 的默认信任范围描述为“单一操作者或互相信任的团队”。这正说明：如果企业有部门隔离、岗位权限、客户数据隔离或跨组织协作，就不能只沿用个人助手的默认运行方式。

## 3. 自然语言、Skill 和程序，分别是什么？

### 自然语言：说清意图

例如：“把这批发票整理好，符合要求的提交报销，不确定的交给财务。”

这句话对人很自然，但系统仍要追问很多问题：什么叫“符合要求”？谁有提交权限？金额上限是多少？税率有问题怎么办？提交到了哪里？

自然语言是一种高层描述。它很适合由 AI 来理解，但它本身不是一份可直接执行的企业制度。

### Skill：给 Agent 的操作手册

Skill 通常会保存提示词、领域知识、示例、工具说明和处理经验。它能让 Agent 越来越熟悉一类任务。

但 Skill 本身通常仍要由模型在执行时理解和选择。换句话说，Skill 像是“优秀员工的工作指南”，不自动等于“企业系统的受控流程”。

只有当关键内容被进一步固定为输入格式、规则、权限、执行步骤、校验和日志时，它才成为真正可交付、可运营的企业能力。

### 程序化工作流：把责任写清楚

程序化工作流不是“所有事情都僵化”。它的意思是把关键步骤显式写下来，例如：

1. AI 识别发票信息，并以固定格式输出；
2. 系统检查发票是否重复、金额是否超标、供应商是否有效；
3. 根据金额和部门路由给对应审批人；
4. 审批通过后才写入财务系统；
5. 留下输入、规则版本、审批记录和执行结果。

这里，AI 依然发挥作用；只是它不再独自决定最后是否执行。

## 4. 为什么高频业务更应采用受控工作流？

### 稳定

同一类业务每天做几百次，不能每次都重新猜测流程。固定路由、结构化输入输出和规则校验，能让结果更一致。

### 成本和速度

Agent 每一次探索都可能需要多轮思考、调用工具、读取上下文。对于重复任务，把已确定的步骤交给程序执行，通常更快，也能减少不必要的模型调用。

需要注意：不是“token 越少就一定越稳定”。真正重要的是：**给 AI 足够但不过量的高质量信息**，避免无关上下文和模糊的工具选择。

### 审计和责任

企业需要知道：这次操作是谁发起的、AI 用了哪一版规则、读了哪些数据、调用了什么工具、谁批准、最终是否成功。

这些记录不是为了增加流程，而是为了在出错、争议、监管检查或复盘时能找到事实。

### 可以持续优化

当某一类例外反复出现时，企业可以先让人处理，再把成熟做法沉淀为规则、Skill 或新的工作流节点。这样，系统会越用越成熟，而不是只积累越来越长的聊天记录。

## 5. 哪些工作适合 Agent，哪些要让系统接管？

### 更适合 Agent 主导

- 研究、调研、内容初稿和方案构思；
- 阅读非结构化文件并提取关键信息；
- 回答开放问题、总结多份材料；
- 处理低风险、少见、步骤无法事先写全的例外。

### 更适合“Agent + 受控工作流”

- 财税：发票识别、报销预审、政策问答、风险提示；
- 制造：BOM 解析、异常归因、工单辅助；
- 服装供应链：跟单信息提取、交期预警、异常处理建议；
- 医疗：知识检索、病历或文档结构化、人工复核；
- 金融与保险：材料整理、风险提示、核保或理赔辅助。

### 必须由受控流程掌握最终执行权

- 资金支付、价格变更、合同对外发送；
- 写入核心数据库、删除数据、修改客户资料；
- 对外承诺、合规申报、授信和高风险决策；
- 涉及敏感个人信息、客户隔离和跨部门授权的操作。

在这些场景中，AI 可以提出建议、完成草稿、识别例外；但是否执行，应由明确的规则、审批和权限体系决定。

## 6. 企业应该搭建什么？

企业真正需要的，不是把很多 Agent、AI SaaS 和知识库拼在一起，而是一套能让团队共同使用、共同积累的 AI 基础设施。

BootX 面向企业交付的 ANC（AI Native Company）架构，核心不是“再造一个万能 AI”，而是四件事：

- **一份公司共享的知识库**：把资料、规则、术语和经验沉淀为 Markdown Vault。原件只在入库时结构化一次；日常回答按目录路由直接读取，Git 负责版本、同步和回滚。
- **每个真人一个自己的 AI Bot**：Bot 对应的是人，不是替代人的“AI 员工”。角色只提供 Persona 模板；每个人保留自己的会话、数据视野、Skill 和成长轨迹。
- **在团队已有的 IM 里使用**：飞书、钉钉、企业微信、Slack 等就是入口，不要求员工再学习一个新的 Dashboard。
- **使用官方 CLI 作为 Harness**：通过 Claude Code、Codex 等官方能力执行，不重新发明一套 Agent Loop；企业侧负责把公司的知识、Persona、Skill、部署和运维组织起来。

可以把它理解为：**一份公司知识，每个真人一个 AI。**

ANC 有两种交付形态：

- 团队已经在用 Agent：先接入云上共享 Vault 与标准 Skill，让大家在现有工作台里共享公司知识。
- 团队还没有 AI 基础：在一台常开设备上托管服务，让每个人在已有 IM 里拥有常驻 Bot。

ANC 不替代 ERP、财务系统或审批系统。涉及资金、客户、数据写入等核心动作时，仍由受控业务工作流掌握最终执行权；ANC 的作用是让 AI 在正确的知识、身份与协作基础上发挥作用。

## 7. 一个容易理解的例子：智能报销

员工上传一张发票后，AI 可以负责读懂图片、提取金额、日期、税号和费用类别。

但后面的工作应由受控流程完成：

1. 检查发票是否重复或异常；
2. 查询员工所属部门、预算和报销标准；
3. 判断是否需要补充材料；
4. 路由到正确的审批人；
5. 审批后写入财务系统；
6. 保存完整的处理记录，并在异常时进入人工队列。

这样做的价值不是限制 AI，而是让 AI 的能力可以放心地进入真实业务。

---

## 8. 我们的主张

> 不要先问：下一步要做哪个 Agent？
>
> 先问：这些 Agent、数据、流程、权限和责任，是否在同一套运行体系里？

未来，单个 Agent 和单项 AI 功能会越来越容易获得。真正稀缺的，是企业自己可持续生长的运行能力：它能让一线人员的使用经验不断沉淀为知识、Skill、工作流和新的业务能力，同时保持安全、稳定和可追责。

## 参考依据（供进一步阅读）

1. Anthropic，《[Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents)》：区分由预定义代码路径编排的 Workflow 与动态决定工具和步骤的 Agent；指出 Workflow 更具可预测性和一致性，Agent 往往以成本和延迟换取开放任务的能力。
2. Anthropic，《[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)》：提出上下文是有限资源；应使用最小、高信号的上下文和清晰的工具集合，避免 context rot。
3. AWS Well-Architected，《[Human-in-the-loop for critical decisions](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec04-bp02.html)》：建议对高风险操作采用风险分级审批，并以确定性策略或规则作为权威控制信号，保留可审计记录。
4. OpenClaw，《[Security](https://docs.openclaw.ai/gateway/security)》：说明单 Gateway 适用于单操作者或互信团队；互不信任用户需要拆分信任边界。
5. Hermes Agent，《[Security](https://hermes-agent.nousresearch.com/docs/user-guide/security)》：说明企业使用 Agent 时需要关注命令审批、容器隔离、凭据过滤与会话隔离。
6. Agent Skills，《[Specification](https://agentskills.io/specification.md)》：说明 Skill 的基础是 `SKILL.md` 指令与可选脚本，Skill 不自动等同于受控业务工作流。
7. HA7CH，《[ai-native-company](https://github.com/HA7CH/ai-native-company)》：BootX 面向企业的 ANC 开源架构，定义了共享 Markdown Vault、一人一 Bot、Persona/Skill 闭环和官方 CLI Harness 的交付形态。
