# 威吉瑞 · 需求确认与方案规划书交付经验

## 背景

为客户「威吉瑞」做财税 AI 转型的需求确认与方案规划书（pre-payment / 意向阶段）。
客户事实（已核验，非杜撰）：财税企业，创始人/法人罗祖威（品牌名"税罗汉"），
成立于 2017-05-17，团队约 30 余人，注册/运营位于横琴。

交付遵循原则：**先定需求，再报价**。用 `bootx-requirements-plan` 技能（已收入仓库
`skills/bootx-requirements-plan/`）跑完整流程。

## 产出

- 产物：威吉瑞《需求确认与方案规划书》（HTML + DOCX + PDF 三态）
- 结构：封面 → 一页纸结论 → 客户背景 → 诊断痛点 → 目标与思路 → 需求模块总览
  → ANC 架构与知识飞轮 → 分期实施规划 → 报价与商务模式 → 下一步与待确认
- 关键结论：把 bootX 定位为「陪跑方」而非工具供应商；用 validation-first 模块化报价，
  先对齐需求与首期范围，再报价。

## 可复用点（重点）

1. **事实交叉核验是第一步，也是最容易省掉的一步。**
   工商数据在 QCC / 启信宝 / 官网 之间经常冲突。做法：三源比对、取可信集合；
   对外文档**绝不直接印冲突数字**，改用"约 / 多家 / 团队约 30 余人"；
   顺手修明显错别字（曾见"横景"→应为"横琴"）。
2. **validation-first 模块化报价，平台受限项必须单列。**
   凡依赖平台约束渠道的能力（如个人微信自动读取/发送），必须拆成独立的
   「技术验证 + 报价」行，绝不打包进首期固定价。
   首期范围由已确认预算 / 入口路径定义，而不是先许诺全部能力。
3. **对外文档语气与排版有硬规则**（见技能 `references/style_rules.md`）：
   无版本号、无破折号（——）、无字面 `**`、用 humanizer-zh 去 AI 腔、
   中性黑金主题、封面插客户 logo。
4. **构建管线 HTML → DOCX → PDF**：
   先用 HTML 做富视觉（封面/彩色表头/卡片/callout/架构图），
   再用 `scripts/docx_blocks.py` 转可编辑 Word，最后 Chrome headless 打印 PDF
   （保留图与配色）。架构图用 `assets/anc_diagram.svg` 改标签即可复用。
5. **方法论支柱**：workflow-first、human-in-the-loop、知识飞轮 / ANC、
   把 FDE 陪跑角色贯穿全文。

## 踩过的坑

1. **未核验数字直接进对外文档** → 客户一眼看出来源冲突、掉信任
   → 规避：对外版只放"约/多家"口径，精确但未核实的数字留在内部版。
2. **平台受限能力打包进首期报价** → 一旦无法交付砸口碑
   → 规避：个人微信自动化等单列「技术验证 + 报价」，首期只承诺已验证能力。
3. **把 bootX 写成工具供应商** → 弱化陪跑价值、压低客单价
   → 规避：全文锚定"陪跑方"角色，强调 FDE 陪跑与知识飞轮复利。
